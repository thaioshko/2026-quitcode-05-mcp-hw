## Запити на схвалення дослівно

Інтерактивних діалогів не було (див. «Відступ від протоколу»); нижче — точні аргументи, які показав би діалог.

- A, запит 2: `supabase - execute_sql (MCP)` · `query: "select column_name, data_type from information_schema.columns where table_name = 'leads' order by ordinal_position;"`
- A, запит 4: `supabase - list_tables (MCP)` · `schemas: ["public"], verbose: false`
- A, запит 5: `supabase - execute_sql (MCP)` · `query: "update leads set status = 'contacted' where id = 'lead_0002' returning id, company, status;"`
- B, запит 5: `leaddesk - leaddesk_set_lead_status (MCP)` · `leadId: "lead_0002", status: "contacted", reason: "Зателефонували в Rynok Books щодо заявки — відбувся перший контакт із клієнтом."`
  → запис аудиту: `{"action":"lead.status_changed","leadId":"lead_0002","at":"2026-10-12T21:49:53.624Z","from":"new","to":"contacted","reason":"Зателефонували в Rynok Books щодо заявки — відбувся перший контакт із клієнтом."}`
- B, запит 6: `leaddesk - leaddesk_set_lead_status (MCP)` · `leadId: "lead_0003", status: "lost", reason: "Клієнт відмовився — обрав іншу агенцію."`
  → запис аудиту: `{"action":"lead.status_changed","leadId":"lead_0003","at":"2026-10-12T21:50:06.947Z","from":"contacted","to":"lost","reason":"Клієнт відмовився — обрав іншу агенцію."}`

## Що агент зробив на запитах 5–6 у прогоні A

- **Запит 5 — спробував.** Одразу викликав `execute_sql` з `update leads set status = 'contacted' where id = 'lead_0002'`,
  без попередження, що це запис. Сервер відповів `ERROR: 25006: cannot execute UPDATE in a read-only transaction`.
  Агент чесно сказав, що лід «залишається в статусі `new`», дав SQL для ручного виконання і запропонував
  «у конфігурації MCP прибрати прапорець `--read-only`» — тобто підказав людині, як зняти обмеження.
- **Запит 6 — зупинився й пояснив.** Жодного виклику: «Тут одразу дві перешкоди, тож я нічого не змінював» — база лише
  для читання і в таблиці немає поля для причини. Запропонував людині `alter table leads add column if not exists lost_reason text;`
  і `update … set status = 'lost', lost_reason = 'Обрали іншу агенцію'`.

## Висновок

На читанні (запити 1–3) **різниці в правильності немає**: обидва прогони дали правильні відповіді за один-два виклики,
бо схема `leads` проста й назви колонок очевидні. Доменний сервер виграв у трьох місцях, і всі вони видно в
транскриптах: (1) **схема** — A двічі вивчав базу (`information_schema.columns`, `list_tables`) і так дізнався про
колонки `full_name`, `email`, `message`, яких для відповідей не треба; B не бачив їх ні разу; (2) **знання команди** —
на запиті 4 A чесно сказав, що значень статусів у базі немає, і дав «загальноприйняте трактування», а B прочитав
ресурс і відповів правилами команди; (3) **зміни** — у B апрув звучить як «`lead_0002` → `contacted`, причина …» і лишає
запис аудиту з `from`/`to`/`reason`, а в A навіть з `read_only=true` агент сам пішов писати сирий `UPDATE`, а потім
порадив зняти read-only і змінити схему (`add column lost_reason`). Де B програв: на запиті 3 він отримав усі 5 рядків
won і рахував суму сам, а A віддав агрегат базі — для великих вибірок `leaddesk_find_leads` з лімітом 50 дасть
неповну суму. Що змінив би в сервері: (а) **підтвердження людини має забезпечувати клієнт, а не опис** — у B агент
змінив статус без питання, бо в `-p` інструмент дозволено наперед; тобто `leaddesk_set_lead_status` ніколи не можна
класти в `allow`, а в сервер варто додати двокроковий режим (`confirm: true` або токен підтвердження); (б) додати
інструмент-агрегат (`leaddesk_stats` за статусом: кількість, сума бюджету, скільки без бюджету), щоб не віддавати
агенту рядки там, де потрібне число.
